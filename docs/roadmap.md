### 6. 로깅 · 관측 · 애널리틱스 — 예정 (L · 높음)

지금은 `src/server/lib/log.ts`의 JSON 로거 파사드 한 개가 전부입니다. 운영에 올리기 전에 가장 먼저 채울 빈칸이고,
**SSR(7)보다 먼저 하는 것을 권합니다** — SSR은 디버깅 난도를 올리는 작업이라 관측 수단이 선행돼야 합니다.

| 하위 작업                                                                                                                               | 규모 | 중요도 |
| --------------------------------------------------------------------------------------------------------------------------------------- | ---- | ------ |
| 6-1. **요청 로깅 + 상관 ID** — 요청마다 `requestId`(응답 헤더 `X-Request-Id`), 메서드·경로·상태·소요 시간, 민감값 마스킹                | S    | 높음   |
| 6-2. **로거 확장** — 레벨 환경 설정, 에러 직렬화(스택), `ctx`에 자식 로거(요청·회원 `sub` 자동 첨부), pino 등으로 교체 가능한 구멍 유지 | S    | 높음   |
| 6-3. **클라이언트 에러 수집** — `window.onerror`/ErrorBoundary → `POST /api/telemetry/errors`, 빌드 버전·로케일 첨부                    | M    | 높음   |
| 6-4. **메트릭** — 요청 수·지연 히스토그램, WebSocket 연결 수, 채팅 메시지율, `/api/metrics`(Prometheus 형식)                            | M    | 중간   |
| 6-5. **트레이싱** — OpenTelemetry. 요청 → 서비스 → DB/Redis. 로그의 `traceId`와 연결                                                    | M    | 중간   |
| 6-6. **애널리틱스** — 페이지뷰·이벤트 수집 파사드(`track(name, props)`), 공급자 교체 가능, 같은 파사드로 서버 이벤트도                  | M    | 중간   |
| 6-7. **동의·개인정보** — 쿠키/수집 동의 배너(디자인 시스템 컴포넌트), 동의 전엔 수집 안 함, `sub`는 해시 후 전송                        | M    | 높음   |

- 의사결정이 필요한 것: 애널리틱스 공급자(자체 수집 vs 외부 SaaS), 로그 저장소. 파사드까지만 이 저장소에서 만들고 공급자는
  다운스트림이 고르게 하는 쪽을 권합니다(검증·i18n·pubsub과 같은 방식).
- 6-1, 6-2는 거의 확정적이고 작아서 바로 착수 가능합니다. 6-7은 6-6과 **반드시 함께** 나가야 합니다.

### 7. SSR — 예정 (XL · 중간)

가장 큰 구조 변경입니다. 지금 클라이언트는 Bun HTML import + SPA 캐치올이라, 렌더 경로가 둘이 됩니다.
"중간"으로 둔 이유: 이 보일러플레이트의 화면은 대부분 로그인 뒤의 도구형이라 SEO 이득이 제한적이고, 이득은 첫 화면
속도와 공유 미리보기에 있습니다. 필요한 서비스가 있을 때 착수해도 늦지 않습니다.

| 하위 작업                                                                                                                                    | 규모 | 중요도 |
| -------------------------------------------------------------------------------------------------------------------------------------------- | ---- | ------ |
| 7-0. **착수 판단·범위 결정** — 전면 SSR vs 라우트별(공개 페이지만) vs 정적 프리렌더. 먼저 결정 문서로 확정                                   | S    | 높음   |
| 7-1. **서버 렌더 진입점** — `renderToPipeableStream`, 라우터(`StaticRouter` 대응), 빌드 산출물 3종(서버 번들·클라이언트 번들·템플릿)         | L    | 높음   |
| 7-2. **데이터 프리패치와 하이드레이션** — TanStack Query dehydrate/hydrate, `ctx.caller`를 서버 렌더에 전달(쿠키)                            | L    | 높음   |
| 7-3. **환경 의존 코드 분리** — `window`/`sessionStorage`(게스트 id)/`matchMedia`(테마) 접근을 SSR 안전하게, 테마·디자인·언어 초기값을 쿠키로 | M    | 높음   |
| 7-4. **개발 모드 HMR 유지** — 지금의 `bun run dev` 경험을 해치지 않기 (Bun HTML import와의 공존)                                             | M    | 중간   |
| 7-5. **React Compiler·번들 파이프라인 정합** — 서버 번들에도 같은 컴파일 규칙, 버전 핸드셰이크 유지                                          | S    | 중간   |
| 7-6. **메타·SEO** — 라우트별 `<title>`/OG 태그, `sitemap.xml`(지금의 `sitemap.json`과 별개)                                                  | S    | 낮음   |
| 7-7. **스트리밍·에러 경계, 서버 렌더 캐시**                                                                                                  | M    | 낮음   |

- 위험: 하이드레이션 불일치, 시간 포맷(UTC → 경계 변환 정책이 서버에서도 일관돼야 함), 로그인 리다이렉트 흐름 변화.
  모두 6번(관측)이 있어야 안전하게 잡힙니다.
- 이 변경은 다운스트림이 머지만으로 끝나지 않으므로 **업그레이드 가이드를 반드시** 씁니다.
